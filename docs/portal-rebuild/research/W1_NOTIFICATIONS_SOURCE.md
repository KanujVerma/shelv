## Exact new API seam

Root [`PortalNotification.ts`](../../../src/contracts/PortalNotification.ts), Values, Validation and Mapping define a strictly closed schema. One browser RPC: `concierge_notification_command_v1(p_command)`, schemaVersion1:

- `list_inbox_v1 {cursor: null | n:UUID, limit: 1..50}`. Recipient is inferred from the real caller; no client/recipient selector.
- `mark_seen_v1 {requestId, deliveryId, expectedRevision}`. Own portal row only. First mark increments revision once; an already-seen row retains its original seen time. Exact retries return the original journal receipt under current authorization.
- `read_event_deliveries_v1 {eventId, cursor, limit}`. Actual human principal plus current VIEW capability and current target enrollment/deletion checks. No recipient address, provider ID or private source content.
- `retry_failed_email_v1 {requestId, deliveryId, expectedRevision}`. Actual human plus current EDIT capability and target/recipient eligibility. Only FAILED retries through the existing retry helper with `false`. UNCERTAIN returns `reconciliation_unavailable`; there is no trusted reconciliation adapter in this slice.
- `request_status_v1 {original: exact mark_seen/retry command}`. The immutable actor/request journal binds normalized UUIDs, original command hash, delivery/event, action and CAS. `committed` returns only the matching original receipt; a missing or purged record returns `unknown`, never `absent`, never fresh success and never a live delivery observation substituted for the receipt.

Agents are denied even if they have unrelated plan grants. Known inactive principals do not fall through to ordinary-client access. Reads/seen operations do not grant care-write authority; read-only entitled access can mark an own notification seen. Own client eligibility requires actual session/enrollment/deletion/entitlement and current care window. Human attention recipients retain the existing emission requirement of VIEW+EDIT, exact current route/owner fallback and configured email flag. Operational advisor status uses VIEW; retry uses EDIT. These are enforced in SQL source, not by a browser role bit or a model-authored field.

Pages are **live keyset scans**, not immutable snapshots: `consistency: live_keyset`, `observedAt`, echoed cursor, bounded items and advancing nextCursor. No total/complete/frozen-clock claim. The SQL inspects at most the requested number of raw rows; revoked/invisible rows can yield an empty advancing page. A null next cursor means no remaining own/raw rows at that observation, not immutable completeness. Late inserts with lower UUIDs require a fresh scan. Responses reject malformed/backward/repeated cursors and private extra fields. Limits are 8,192 command bytes, 100,000 response bytes and50 items.

Event facts distinguish publication, Care, Review and published guidance. Source validation checks actual stored publication/output/event/attention/request linkage. Destinations bind to that source: publication -> actual `/history/versions/N`; guidance -> actual `public_review:ID`, `public_instruction:ID` or `public_reply:ID` history key. Care/Review advisor direct resolution is explicitly `unavailable / advisor_review_resolution_unavailable`. No private A07 URL is guessed.
