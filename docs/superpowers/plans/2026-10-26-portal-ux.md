# Shelv Portal UX Implementation Plan

> **For agentic workers:** Use the current delegated implementation workstreams and verify each bounded change before integration. The user authorized autonomous design, implementation, tests, commits and push to PR #209. No merge or deployment is authorized.

**Goal:** Make the complete client and advisor experience predictable, coherent and concise without changing business truth.

**Architecture:** Keep task-first Plan navigation with Recommendations and Daily routine, selecting the first relevant view from canonical state. Place About this plan and version history with the plan, and account, payments, service, help and optional tour replay in recognizable secondary account navigation. Use shared vanilla HTML/CSS/JavaScript primitives and existing domain projections; no framework migration or animation dependency.

**Tech Stack:** Vanilla JavaScript modules, semantic HTML, CSS, Node >=22.23.0, Playwright synthetic browser fixtures.

**Spec:** [Design and rationale](../../PORTAL_UX_DESIGN.md), the founder's 26 October full UX mission, `docs/CONCIERGE_FOUNDER_OPERATIONS.md`, `docs/PORTAL_ACCEPTANCE.md`, `.claude/skills/shelv-ux-review/SKILL.md`, `.claude/skills/shelv-design-polish/SKILL.md`.

## Constraints and baseline

- Preserve cream/forest-green identity, privacy/permissions, drafts/publications, optional choices, approval/payment/receipt/Start, private notes and client-visible replies.
- All browser work is local, synthetic and network-intercepted; unexpected requests fail closed. No real account writes, messages, transactions, permissions or deployment.
- Original PR #209 head: `bc4568e4e3af0936fd027351002f65b77512e00d`. It lacked newer implemented/deployed walkthrough/service work from PR #208.
- Six exact source commits were cherry-picked with `-x`, without merging any PR: `87ad5a9` -> `dd31397`, `0d5e6f7` -> `93b3754`, `44c3d37` -> `589602a`, `db6b8e9` -> `202378f`, `b22436f` -> `c7ba4c4`, `2901f6c` -> `de69880`.
- Integrated baseline is `de69880`. Its tree differs from original #208 only in the original four PR #209 skill/instruction files. This integration is local and unpublished.
- Prefer task-first entry over a new Home dashboard: a dashboard would duplicate existing routine/recommendation work. Pending choices and received-but-unstarted products open Recommendations; otherwise existing routines open Daily routine. Explicit navigation/history takes precedence. No plan uses actual availability/payment status.
- Account identity must come from an explicit trusted identity or authenticated own-record projection. Never parse a plan title. Unknown names use Your account; fictional sample names are explicit.

## Write-set ownership and integration contracts

| Workstream | Exclusive files | Shared contract |
| --- | --- | --- |
| Foundations | All portal CSS, `site/ui/*`, `tests/ui-system.test.mjs`, `package.json` UI enforcement script, contributor UI/copy guidance | `createPortalDialog({document=globalThis.document,className='advisor-dialog',onClose=null}={})` from `site/ui/dialog.js` returns `{element,open({title,content,trigger=null,initialFocus=null}),close(),dispose()}`. `content` is trusted escaped markup or a Node; `initialFocus` accepts Element/selector/function; `open` returns element and sets accessible name, opening focus; Escape/Close restore trigger and scroll; caller wires domain actions. Existing `.solid`, `.quiet`, `.text-button`, `.nav-item`, `.advisor-panel`, `.view-tabs` consume shared tokens. No domain state imported. |
| Client | `site/client/*` except shared ingredient-library data, `site/portal.js`, `site/maya/client.js` mount only, `site/walkthrough/viewer.js`, client UX tests and HTML entrypoints; `tests/service-browser.test.mjs` baseline clock repair | `mountClientPortal` adds explicit `account` input and consumes canonical optional account display name when available. Preserve `onReady` API (`navigate`, `openOverview`, `openProduct`, `openRoutineProduct`, `openCart`, `closeDialog`, `getDialog`, `selectCategory`) for guides. Preserve manageHistory=false viewer isolation and synchronous selectors needed by anchors. |
| Advisor | Advisor JavaScript workspace/navigation/editor/admission, feature check-ins/payments JavaScript, advisor focused tests | Consume same dialog helper and tokens. Existing domain requests, DraftSession, saved preview target checks and feature mount contracts stay authoritative. Do not edit client composition or shared style.css. |
| Root integration | Final acceptance/provenance/research docs, overall tests and diff; client owns HTML entrypoints and foundations owns package UI checks | One writer integrates shared dependencies, handles cross-workstream conflicts and decides optional account wire projection with client worker. No unattended merge/deploy. |

All paths above are relative to `apps/portal/` unless otherwise stated. Agent assignments and changing test results live in ignored controller progress, not competing operating-policy documents.
